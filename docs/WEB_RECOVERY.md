# 웹 저장소 백업과 복구

이 절차는 운영자가 선택한 SQLite 파일을 다루는 수동 도구다. 자동 백업 일정이나 운영 배포를 설정하지 않는다. 먼저 폐기 가능한 가상 자료로 연습하고, 실제 운영 파일은 담당자가 경로·보관 기간·접근 권한을 확인한 뒤 사용한다.

## 백업 파일 만들기

기본 웹 Python 환경에서 저장소 루트의 명령을 실행한다. 아래 `/path/to/...`는 운영자가 바꿀 예시 경로다. 원본 파일은 현재 사용자 소유의 `0600`, 원본과 출력 디렉터리는 현재 사용자만 접근하는 `0700`이어야 한다. 출력 디렉터리는 먼저 준비하며, 파일은 이 소스 checkout 밖에 둔다. 도구가 다른 저장소의 추적 여부까지 검사하는 것은 아니므로 다른 Git 저장소에도 백업을 두지 않는다.

```bash
.venv/bin/python scripts/fortune_web_snapshot.py backup \
  --source /path/to/private-data/web.sqlite3 \
  --destination /path/to/private-snapshots/snapshot-new.sqlite3
```

`backup`은 세션·프로필·집계 영수증을 포함한 **개인정보가 있는 전체 복사본**을 만든다. 파일을 공개 저장소, 이슈, 테스트 산출물에 첨부하지 않는다. 백업 보관·폐기와 저장 장치의 보호는 운영자가 관리한다. 이 도구는 암호화나 외부 보관을 제공하지 않는다.

파일 복사 명령 대신 [SQLite Online Backup API](https://www.sqlite.org/backup.html)를 사용한다. WAL에만 기록된 커밋도 반영하며, 출력은 부가 WAL 파일 없이 열 수 있는 SQLite 파일이다. 현재 앱의 테이블·열·기본키·외래키와 무결성을 확인한 뒤 새 파일을 게시한다. 원본의 응용 데이터와 메인 DB 내용을 변경하지 않지만 SQLite가 원본 옆의 WAL/SHM 관리 파일을 만들거나 갱신할 수는 있다.

기존 출력 파일, `-wal`·`-shm`·`-journal`이 남은 출력 경로, 심볼릭 링크는 거부한다. 출력은 `0600`이며 기존 파일을 덮어쓰지 않는다. SQLite 복사·검사의 기본 작업 예산은 10초, `--timeout`으로 최대 60초까지 지정할 수 있다. 파일시스템의 동기화 호출 자체를 강제로 중단하는 제한시간은 아니다. 잠금이나 검사 실패 시 원인을 담은 DB 내용·경로를 출력하지 않는다. `publication_uncertain`이면 파일 게시 후 디스크 동기화 또는 정리에 문제가 생긴 것이므로 출력 경로를 비공개로 확인한 뒤 재시도한다.

## 삭제한 프로필을 되살리지 않는 복구

옛 DB를 그대로 교체하면 백업 이후 삭제한 프로필과 세션이 돌아온다. 현재 세션 쿠키는 서버 키로 서명된 구매권이 아니라 DB에서 해시로 찾는 값이므로, `SECRET_KEY`만 교체해도 옛 쿠키가 무효화되지 않는다.

제공하는 복구 명령은 **날짜별 합계만 복구**한다. 새 DB에 허용된 이벤트·화면의 합계만 넣고 세션, 프로필, 세션별 영수증은 복사하지 않는다. 기존 브라우저는 출생정보를 다시 등록해야 한다. 백업 이후의 최신 합계는 복구되지 않으며, 계정·구매 권리 복구 기능도 아니다.

```bash
.venv/bin/python scripts/fortune_web_snapshot.py restore-aggregates \
  --source /path/to/private-snapshots/snapshot-new.sqlite3 \
  --destination /path/to/private-recovery/recovered-new.sqlite3
```

복구 대상은 서비스가 사용하지 않는 새로운 경로여야 한다. 이 명령은 서비스를 멈추거나 설정을 바꾸지 않는다. 세션을 포함한 완전 복구는 지원하지 않는다. 백업 이후의 삭제·만료를 반영할 별도 기록과 검증 절차가 없기 때문이다.

새 파일을 운영에 연결하기 전에는 다음을 확인한다.

1. 격리된 앱에서 옛 쿠키를 넣어도 프로필이 돌아오지 않는지 확인한다.
2. 새 등록·조회·삭제가 작동하고 날짜별 합계만 보존됐는지 확인한다.
3. 서비스 중지·전환·실패 시 원복 절차를 정한 뒤 운영 경로를 변경한다. 사용 중인 DB 파일 위에 복사하지 않는다.
4. 실제 삭제 요청은 원복용 DB에도 반영돼야 한다. 전환 실패를 이유로 삭제 전 프로필을 포함한 옛 DB를 그대로 재연결하지 않는다.

## 가상 자료 회귀 검사

```bash
.venv/bin/python -B scripts/run_fortune_tests.py \
  tests/test_fortune_oracle_web_snapshots.py \
  tests/test_fortune_oracle_web_storage_contention.py
```

전체 백업의 WAL 반영, 손상·스키마 오류 거부, 출력 충돌·권한·시간 제한·실패 정리, 합계 복구 후 옛 쿠키의 프로필 접근 거부를 확인한다. 가상 자료 검사 통과가 운영 백업의 존재나 실제 장애 복구 완료를 뜻하지 않는다.
