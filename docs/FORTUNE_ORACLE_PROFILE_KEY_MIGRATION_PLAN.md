# Profile Key Migration Plan

상태: **PENDING**. 이는 legacy 자료가 있는 설치에 적용하는 이관 계획이며, 현재 소스의 사용자별 키 구현이나 운영 서비스 검증을 대신하지 않는다. 새 설치의 빈 store에는 이관할 자료가 없다.

## 목적과 전제

legacy `telegram:default` 자료를 신뢰된 gateway context의 `telegram:<user_id>`로 옮긴다. 소스·대상 사용자 소유 관계를 운영자가 확인할 수 있어야 한다. 메시지 본문의 ID만으로 이관 대상을 정하지 않는다.

- gateway가 검증된 `platform`과 `user_id`를 전달하는지 먼저 확인한다.
- 승인된 store의 비공개 백업과 복구 절차를 준비한다. 실제 경로나 원문 자료를 공개 문서에 기록하지 않는다.
- 실제 이관에는 **explicit user approval**이 필요하다. 자동 시작이나 덮어쓰기는 없다.

## Dry-run

1. 원본 `profiles.telegram:default`의 존재와 스키마를 확인한다.
2. 대상 `profiles.telegram:<user_id>`의 존재 여부를 확인한다.
3. 대상이 이미 있으면 중단한다. 원본만으로 소유 관계가 불명확해도 중단한다.
4. 계획에는 복사/충돌 여부와 필드 존재 여부만 남긴다. 실제 키, 이름·출생정보, secret 또는 그 해시를 출력하지 않는다.

Dry-run은 store를 쓰거나 삭제하지 않는다. 합성 임시 store에서 먼저 충돌·실패 경로를 확인한다.

## 승인 후 실행과 복구

1. 원본을 보존하며 확인된 대상 키로 복사한다.
2. 대상 스키마와 사용자별 조회·수정·삭제 격리를 확인한다.
3. 원본 제거는 검증 이후의 별도 명시적 승인으로만 수행한다.
4. 실패하면 더 진행하지 않고 승인된 백업으로 복구한다. 대상 키를 원본으로 무조건 덮어쓰지 않는다.

이 후보본에는 자동 이관 도구나 실사용자 매핑을 추가하지 않는다. local 테스트 통과를 live 다중 계정 검증 완료로 표시하지 않는다.
